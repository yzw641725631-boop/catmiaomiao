# 工作报告：界面与开源方案对比 v1.0

日期：2026-10-31（Asia/Shanghai）。项目：openmaus-assistant。任务：用户觉得自己用 AI 做的界面不好看，要求阅读 install.md 了解项目，找界面更好看的同类开源项目和类似 Grok Bot / Muse 的开源个人助理，并分析现有代码。

读取 install.md、AGENTS.md、main.md、本项目概览与 10-23 开源研究。用户选择：HTML 对比页；也评估换底座；人物陪伴和工作区两种方向都看；分析前端 UI 加整体架构。本轮只调研和记录，没有改 app/、adapters/、upstream/、runtime/，没有启动或停止服务。

## 结论

1. 不建议换底座。OpenMausBot README 自述为开源 Grok Bot 替代，Apache-2.0（enterprise/ 除外）。OpenClaw（MIT，约 39 万星）是唯一值得长期观察的替代，但 Gateway/会话/记忆模型不同、前端是 Solid，adapters 基本要重写。Rakazo、Hermes Agent、Super Agent Party、Project AIRI 各有缺口，见对比页第 3 节。
2. 真正的底座问题是升级锁定：workspace-hook.mjs 加载时改写上游 server/index.ts、server/store.ts、server/drivers/chat-mcp-tools.ts，共 12 处替换，各有 SHA-256 锁定；11 个 adapters 文件直接引用 9 个上游内部模块，含 server/testing/ports.ts、cleanup.ts。
3. 界面问题主要是实现偏离已批准效果图：右侧面板占画面 28.7%（效果图 12.7%），输入框变成双层厚卡并压住人物，顶栏三种按钮形状。CSS 6 个文件 87KB，402 种不同色值、17 种像素字号、26 种圆角写法、41 处 !important、75 个类选择器跨文件重复定义。App.tsx 52.5KB/388 行，最长行 2,046 字符，34 个 useState；界面由 evidence/apply-interaction-ui.mjs 一类锚点替换脚本修改。
4. 最该借的是上游自带界面：src/ 674 个 TS/TSX 文件（约 5.2MB，不含测试），Tailwind 4，有浅色主题与 zh/zh-tw；ApprovalCard、AskCard、ComputerPanel、GoalRunCard、RoutineCalendarPage 现成，但依赖上游 store/i18n，需要整层接入。人物方向借 Lobe Vidol 构图、TalkingHead 动态、ElevenLabs UI 语音球；工作区方向借 Muse 状态/目标视图、Eigent 右栏分组、assistant-ui 对话组件。
5. 其他风险：agent_project 与本项目都不是 git 仓库；evidence/ 1,618 项，其中 workspace-contract-* 458、services-contract-* 218 个测试临时目录未清理，本轮 find 截图 120 秒超时。

## 追加：工作中补充一句、另开任务（同日）

用户补充要求：像 Grok Bot / Muse 那样，工作中再发消息能接着补充，说的是另一件事就另开子代理。按代码核对，写入对比页第 5 节：

1. 主对话这一轮还在跑时补一句：上游 acceptDirectSend 走 admission direct-busy，openai-chat 驱动的 steer 把话放进 asides，在下一轮模型决策前插入；带图片插不进则排队。前端 useCompanion 只识别 queued，插入成功无提示；runtime.mjs 451–456 行每次发送都附加约 1,400 字固定说明，外加实时状态和能力清单。
2. 工作已由 assistant_start_work 交出后补一句：消息进的是主对话。liveWorkNote 只遍历 helperIds，不列主助理自己的工作；没有“补充到某项工作”的工具；CHIEF_TOOL_SCOPE 不含上游 list_threads/start_thread；WorkDetail 无输入框；native-goals.mjs 在目标执行中返回 409。这是用户所说问题的主要原因。
3. 另一件事：assistant_start_work 新开独立工作，10-23 并行验收通过（interaction-concurrent acceptance.json）。上游每 bot 默认最多 3 条线程同时 busy（等待小助理回报的线程不占名额）。
4. 对照：Muse 官方原文支持中断和连发多个任务，复杂主题用旁聊；Grok Bot 官方指南未写工作中补充的处理【未找到原文】；OpenClaw /queue 默认 steer，另有 followup/collect/interrupt，子代理默认每会话 8 个并行。
5. 建议（未实施）：新增“补充到工作”工具并在回执中区分插入/排队；实时状态列出主助理开着的工作；工作详情页加输入框；前端显示插入、排队、新开三种回执；插话时不再附长说明；目标执行中补充改为排队。只改 adapters/app，不改上游。已作为对比页第 6 节第 3 步。
