# 对话窗口与连续沟通修复工作报告 v1.0

日期：2026-10-23（Asia/Shanghai）。项目：openmaus-assistant。用户明确指出卡片外观、看不懂文档助理回复、对话卡住；要求继续。本轮在既有本地开发和用户明确修改范围内完成，没有改人物/场景或其他项目。

## 已确认的问题

1. 右侧此前的有限高度和卡片层级把工作正文淹没在参数、历史审批与日志中；模型能力提示也原样混进用户消息。现在是可连续阅读的纸色对话窗，用户气泡/助理正文、工作结果/执行过程、文件正文/差异分开。完整历史保留。
2. 原始记录存在同一语音约 100ms 内两次发送，各有 sendId；只有第一条取得对应回复。旧 QA 页面此前也曾开启持续录音，是重复采集的一个可能来源，不能只凭该时间差确定唯一来源。现增加全服务单页面语音会话、逐次采集完成防重；当前已证明的终态回复不会因旧派工 requestPending 永久阻塞，45 秒等待后继续听且不重发，另有主动继续说话入口。
3. 桌面任务已在后续原生通知中失败（the person did not answer），旧 needs-input 卡却继续计入待处理。现在核对相同真实目标线程的超时通知，关闭问题并显示未完成；主助理输入前附当前实际工作状态，避免从旧文字推测“仍在跑”。没有替用户授予桌面读写权限。
4. 本轮检查时 5217 曾无监听，确实无法回复；恢复后长对话又暴露 SQLITE_CANTOPEN。隔离环境设置了 TEMP/TMP 等路径却没有创建。合成 SQLite 文件临时表复现：缺目录失败，建目录后 20000 行通过；运行时启动补齐隔离 temp/cache/appdata 目录。首次两条检查失败/排队历史保留，后续真实新请求连续成功。
5. 新预览页下载曾使用相对文件名，和原生消息允许的真实文件链接不一致，实测失败后修正为精确链接。最终浏览器下载 report.md 的 SHA-256 与原生文件一致。
