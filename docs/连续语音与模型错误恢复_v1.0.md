# 连续语音与模型错误恢复 v1.0

日期：2026-10-22。范围：用户明确要求停顿 2 秒再发送、开启后连续语音直到“转为打字”，并排查发送后的 502。沿用已批准本地首版的 G2/G4；本次交互由用户直接指定，未改人物与主布局。当前是开发者自检，G5 未独立终签、G7 未申请。

## 2026-10-28 当前模型重试补充

Saturn 的 `MODEL_UPSTREAM_WEB_VERIFICATION` 503 现在与普通临时模型错误采用同一条安全边界：只有在任何文字、推理、工具调用或其他事件交给原生内核之前，才自动重发最多两次（300 毫秒、900 毫秒退避，90 秒窗口）。这是新的上游请求，会给账号调度器重新选号的机会，但不保证强制换号。已经开始输出或已经发出工具调用时不重试，所以不会重复电脑/文件操作。语音层仍不会重新发送整条用户任务；失败记录和用户文字继续保留。

## 当前行为

首次打开页面点击一次“开启语音对话”，浏览器许可和音频上下文由这个动作启动。此后一句话识别并发送，等对应主助理回复播完后自动继续听；不再要求每轮点麦克风。点击“转为打字”会取消麦克风、清除待播报意图并停止声音，迟到的 ASR、模型或 TTS 不能重新开麦。刷新页面或重新进入浏览器后仍需首次开启，不绕过浏览器权限。

| 状态 | 行为 |
|---|---|
| 倾听 | 采集已选麦克风，显示真实输入音量；有效人声后连续静音 2000ms 才结束 |
| 等待回复 | 结束音频并等待 ASR end，发送最终文本一次；按 sendId/requestMessageId 等待本次请求 |
| 播报 | 对应的成功回复自动播放，播完约 300ms 后继续倾听；可以打断并说话 |
| 打开设置或暂时断线 | 暂停采集与播放；关闭设置或重连后继续语音 |
| 静音等待 | 不发空聊天；长时间无语音时结束并更新音频连接，保持语音模式 |
| 模型失败 | 保留失败记录和已发送文字，提示模型未回复，继续听下一句，不自动重发整个用户任务 |
| 麦克风硬错误 | 提示权限、设备消失、独占或采集暂停，等待检查；不反复弹权限 |
| 后台工作已接受 | 恢复倾听下一句，后台派工继续在工作记录里运行 |

当前为轮流说话：模型思考和播报时暂停采集，防止把助理自己的声音当成下一句。没有宣称全双工插话或人物口型。

原实时中继还保留着 `silence_duration_ms:800`，客户端又把服务端 VAD final 当成整句发送，这会绕过本地静音时间。现本地 VoiceActivity 与上游 VAD 参数均为 2000ms；服务端分句只累积文字，不能越过本地两秒停顿提前发送。手动“现在发送这句话”仍可立即结束。

## 耳机输入修复

增加“声音 → 麦克风”的设备选择、音量表和本地测试。选择保存在当前浏览器的本地偏好中，指定设备不可用时明确报错，不静默改成其他输入。请求浏览器自动增益；采集使用设备原生采样率，经原有 AudioWorklet 重采样到 16k PCM。

旧固定 RMS 门槛 0.012 会丢弃较小的有效输入；现为 0.003，并允许未过门槛的非零音频交给 ASR，空识别结果不发送聊天。浏览器已实际收到 USB PnP 麦克风数据，用户确认音量随说话变化，并确认修复后的语音文字自动发送且有回复。该结论不等同于已测完各种噪声和耳机。

本地音量测试只在本机处理，不保存、上传或回放原始声音。正式语音对话按现有授权发送给 ReachAI ASR。

## 502 / 503 调查与恢复

最新主助理与文档助理失败已定位：当前 DeepSeek 上游 HTTP 503，ReachAI 服务端日志给出 `upstream_web_verification`，即上游要求网页验证、本次账号尝试耗尽。主助理与短上下文的文档助理均在输出前失败，不能归因于麦克风或仅仅上下文过长。旧 502 包装已修正：503 保持 503，已知网页验证错误映射为 `MODEL_UPSTREAM_WEB_VERIFICATION`，显示更换模型/处理上游验证的提示；当时的本地适配尚未重试这类错误，后续已由上方 2026-10-28 补充改为无输出时有限重发；普通临时错误仍有最多两次重试。没有尝试绕过网页验证或改动线上账号池。

原生派工请求会为后续恢复保留 `requestPending:true`，即使本轮已有明确的 `tool.terminal && ok:false` 模型错误。VoiceReplies 现以同一 requestMessageId 的最新终态回执结束语音等待；不把较早的“已派工”当成成功答复，不修改内核历史或自动重发任务。对应失败会提示并自动续听，迟到的旧回复不播报。

重启后当前主助理带 43 条上下文、4 个工具定义、35723 字节请求约 11.78 秒成功返回；模型自身约 10.63 秒。此次成功只证明该次恢复，网页验证导致的服务波动没有根治。当前保留用户选择的 DeepSeek，已向用户提供临时切换既有 agens 的选择，未获回复前不替换；agens 先前有慢响应/超时，不能承诺其稳定性。

原始服务端错误的脱敏观察记录：`evidence/microphone-20261022/provider-verification-observation.json`。

语音已识别、已发送之后的失败发生在 LLM 请求阶段。ReachAI 的 `OpenAiCompatibleRuntimeClient.chatStreamEvents` 会把供应商非 2xx 或连接异常转成模型错误事件；此前本地适配把这些模型流错误统一包装为 502，原始状态被隐藏。不能仅凭前台“502”断言每一次都是同一云端故障。

本次直接对现有实例发送短合成测试，不包含用户音频或聊天内容：

- 当前用户已选 `deepseek-hongkong` / `deepseek-v4.1-flash`，3 次流式短请求均成功，约 4.12、3.36、2.89 秒。
- 此前使用的 `agens` / `agnes-3.0-flash`：2 次成功但约 11.42、39.68 秒，第 3 次在本次探针的 45 秒时限超时。显示明显波动，不能据此进一步断言其供应商内部故障原因。
- 更新后通过真实主助理、当前会话历史和工具定义验证：31 条消息、4 个工具定义、请求约 32638 字节，模型约 9.55 秒完成，主助理总约 10.35 秒返回成功。并非只验证了无上下文短请求。

沿用用户当前选择的 DeepSeek；开发未自动切换实例或修改线上平台。模型流增加最多 2 次短暂重试（共 3 次），仅用于没有任何文字、推理或工具调用输出时的临时错误。已经输出的部分结果和工具调用不会被适配层重播；参数或鉴权错误不重试，中断会取消退避。网络/响应超时与上游 HTTP 状态分别标识，失败不伪装为成功。

本项目 `runtime/logs/model-requests.jsonl` 只记录请求标识、实例 ID、消息/工具数量、字节数、耗时、重试与错误码；不记录提示词、识别文字、音频、厂商地址或密钥。云端偶发错误仍可能发生，此处实现的是有限恢复和可定位证据。
