# 动态小助理接入与验收 v1.0

日期：2026-10-23（Asia/Shanghai）。适用：OpenMausBot v0.1.121 / `97a4a1cab96ab3d07b0c7dac275f69afc6e7a8dc`，本机同源服务与 React 前台。用户已澄清此前口述需求为“创建小助理”。本轮接通原生创建、动态成员、派工、回报和持久恢复；Computer Use、Skills、连接器和整体工作区重设计仍见研究草案。

## 使用入口

刷新 `http://127.0.0.1:5217/`。可以在主对话中说“帮我创建一位行程助理，负责规划行程，先给两种选择”；主助理使用原生 `create_bot`，实际应用成功后显示创建回执，新成员进入团队。也可以点左下“添加”，填写名字、职责、工作方式；提交中的按钮禁用，失败显示在表单处，重试复用原请求。

“我的小助理”列出全部实际成员，左下常驻区域只保留最近两名，防止团队变大后遮住人物。点“安排工作”回到任务输入，预填助理名称，用户补充目标后发送。创建成功并不代表尚未执行的任务已经完成。工作结果沿用原生 thread、真实文件和检查回执。

打开团队抽屉暂停持续语音，关闭后沿用原有恢复规则；不会取消后台任务。进入表单聚焦名字；提交和创建成功后焦点留在弹窗；Tab/Shift+Tab 循环，Escape 关闭并恢复入口焦点。安排工作时将焦点交给输入框。新成员和任务关联重启后保留。

## 原生接入与权限

- 不另建 Agent 循环，不修改上游 checkout，不安装新的第三方运行底座。Chief 在既有工具范围上只增加 `mcp:agents:create_bot`；小助理不能继续创建成员。
- `adapters/team.mjs` 定义成员输入、工具范围和按 Chief 绑定的追加登记。模型创建经固定摘要校验的 Store 加载钩子，在原生 `applyTeamSetup` 应用时记录实际新成员。固定 `server/store.ts` SHA-256 为 `4fbd16bca4c705399657cacb64c6252901c46dad27d20b1a133b6380e8545a35`；版本不匹配即拒绝加载，升级需重新审计。
- 当前原生版本对本地所有者的创建通常直接应用，并生成 `set_up_team` applied 回执；不能把它描述成必须额外确认一次。界面根据实际 applied/pending/failed/expired 等结果显示，不能因为卡片 answered 就显示“已创建”。文件等执行仍按原生逐次审批。
- 新成员默认沿用当前模型，`approvalMode=ask`，工具只含既有 agents、workspace、assistant 范围；computer off、browser false、composio false、无额外 MCP server、非 Chief。不扩大到任意终端、整盘或其他账户。
- 手动创建使用同源认证的 `POST /companion/team/specialists`，仅接受 UUID sendId、name、role、instructions。原生 bot ID 复用 sendId，名称/职责单行长度分别不超过 80/120，工作方式最多 1000；重试幂等，相同 ID 的不同内容、重名和注入权限字段拒绝。
- `refreshTeam` 仅接纳原有种子成员及当前 Chief 登记、同 section、未隐藏且权限匹配的成员。同 section 中不相关的 bot 不因存在就获得本项目文件工具权限。成员刷新同时覆盖 IPC、服务 actor、工具目录、SSE 和任务祖先检查，解决“创建可见但派工工具拒绝”的断链。
- `runtime/live-session.json` 保存稳定身份、种子及动态成员；`runtime/team-members.jsonl` 为登记来源。模型凭证仍只读现有服务端设置，未改平台 Key、云端实例或所选模型。
