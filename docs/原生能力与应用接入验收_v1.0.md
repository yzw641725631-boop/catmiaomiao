## 接入方式

OpenMausBot 仍固定 v0.1.121 / `97a4a1cab96ab3d07b0c7dac275f69afc6e7a8dc`，上游工作树保持干净。`adapters/workspace-hook.mjs` 只在启动加载时，对 SHA 固定的 index/store 应用局部挂接：技能进入原生审核、原生例行线程获得受限目录、目标房间接入同一文件工具，并收紧目标内重复的派工工具。锚点和哈希变化即拒绝启动，需要重新审阅。

Windows 驱动由现有 CUA SDK 的 EmbeddedCuaDriverHost 启动，复用原生连接描述和工具目录。官方固定 ZIP SHA-256 为 `1f4bfceeab64cb7f56be7aad774c3dc2d2910d1427e4be1d79939c706e8029ba`；原始 exe 为 `dbbd52d75759900155fbf3d5f0a13c759a12d06ef17338b88b3f2b8b9c1ef8dc`。安装器尊重现有启用的 Windows 代理，未更改系统代理或 TLS 校验。Windows Node 子进程以私有 IPC 触发原生优雅关闭，避免强杀后遗留 Chrome。

原生例行任务先以关闭状态创建，再登记归属并启用，执行前为它创建独立目录。父进程根据原生 run/thread 证明归属后绑定任务；派遣链继续逐级校验。持续目标同样根据原生 group、精确成员和 thread 校验，只能触达它自己的目录。手工创建、模型创建、普通工作、例行工作和目标没有共享一份伪进度。

本轮未完整接入通用 MCP Apps Host。已进一步核对 MCP-UI AppRenderer 7.1.1 的资源、双 iframe 沙箱、回调契约；普通文件阅读器不冒称标准 Apps。完整的外部 ui:// 资源及原生工具审批回传仍属于后续扩展，不能把装一个渲染包当作完成。原生事件触发也尚未通过真实账户事件验收。

## 邮箱适配的必要修正

复用 [mcp-ecc](https://github.com/karljsamuel/mcp-ecc)，未复刻它的 provider。固定发布包 0.6.0 的实际代码与当前 README 不完全一致，适配层作以下收紧，未修改 npm 包：

- SQLite 存储使用原库表与迁移，凭据和 OAuth 状态改用 Node AES-256-GCM，随机本机密钥；未知旧格式拒绝解密。本地密钥不是 Windows Credential Manager。
- 原包把 health 固定返回 unknown；本地把实际测试状态与检查时间持久到自身配置字段，恢复后仍以实际测试为准。
- IMAP/SMTP 使用真实邮箱地址作用户名，修正原包传 account UUID 的问题；SMTP 证书校验保持开启。
- Native MCP 只暴露 10 个读取工具；账户单独允许写入后，才增加发送邮件和创建/修改日程。账户管理、删除、联系人工具不挂出，停用/外部 owner 的账户不可访问。每次操作仍经过原生工具确认。
- OAuth 使用库的 state/PKCE；回调只监听 127.0.0.1。错误 state 不取消有效登录。保存前向服务确认实际邮箱身份，错选账户不会覆盖原有账户。敏感信息不进入模型提示、页面列表或错误详情。
- 已增加云账户重新登录与 IMAP 更新授权码入口。填写/登录完成后测试账户，再在“分配本领”选择“邮箱与日历”。

适配所依赖的 storage/MCP server JS 文件也固定哈希，升级须先复核。测试中所有密码、token 和邮箱均为合成值；本轮没有用户 OAuth Client ID、授权码或私人 token。

## 旧版会话恢复修复

更新日常实例时发现：旧版隐式 browser=true 和旧工具范围与新配置不同，内核在未结束的原生工作上拒绝修改设置，返回 409。只覆盖配置或跳过内核门控都不合适。适配器对这一类已确认的冲突，先通过原生 interrupt 停止受影响线程，再应用权限，记录迁移元数据，保留原消息与未批准的工具；没有自动批准或重发写入。

原生启动恢复还可能先等待父进程目录校验，而父进程尚在初始化团队。对确实正在迁移的 bot，父进程立即结束其待处理的目录请求，让原生停止能完成；其他助理仍保留原初始化门槛。已分别验证旧浏览器状态、旧动态成员工具范围，以及确定性制造的启动期间目录等待，历史与身份恢复均通过。日常实例随后已正常启动；失败日志和隔离复现保留。
